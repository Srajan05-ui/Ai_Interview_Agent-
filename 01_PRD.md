## 1. Vision

An AI-powered mock interview platform focused on **AI/ML & software engineering interviews**. A candidate uploads a resume (and optionally a job description), gets an ATS score + improvement suggestions, then takes an adaptive voice/text interview (technical Q&A or live coding) that reasons on their previous answers, mimics real company interview styles, and ends with a rubric-based scorecard showing strong/weak topics plus a generated learning roadmap. All sessions are stored so candidates can track progress over time.

**Positioning:** "Built for AI/ML engineering interviews" — not a generic interview simulator.

## 4. Core Features (MVP scope — do not cut)

### 4.1 Auth & Onboarding
- Sign in with Google or GitHub for MVP. Phone number (OTP) is a planned post-MVP addition — deferred because it's the one auth method that isn't free at real usage volume, and this project runs on a **$0 budget** (see Tech Stack doc §2a for the full zero-budget architecture decisions this drives throughout the stack).
- Basic profile: name, target role, target companies (optional), experience level.

### 4.2 Resume/JD Upload & Analysis
- Upload resume (PDF/DOCX). Optional: paste/upload target Job Description.
- AI parses resume → extracts skills, projects, experience, education.
- Generates **ATS Score** (0–100) with sub-scores (formatting, keyword match, structure, quantification of impact).
- Generates specific **improvement suggestions** (bullet-level, not generic).
- Extracted skills feed directly into the interview question-selection engine.

### 4.3 Interview Setup
- Candidate selects: **Interview Type** — (a) Technical Q&A, (b) Live Coding.
- Candidate selects **language** for the interview (question translation layer — see 4.7).
- Candidate optionally selects a **company style** (e.g., Google-style system design heavy, Amazon-style behavioral/STAR heavy, startup-style DSA heavy).
- Permissions requested up front: **Microphone, Camera, Screen Share** — interview cannot start until granted.

### 4.4 Live Interview Experience
- **Voice conversation**: candidate speaks answers; speech-to-text transcribes; AI responds via natural voice (TTS), streamed (not full-wait) to reduce latency.
- **No repeated/duplicate transcript chunks** — dedupe filler/streaming artifacts in the live transcript (this is a transcription UX bug class to solve, not a "training" feature).
- **Adaptive follow-ups**: next question is generated by reasoning on the previous answer (e.g., if candidate misexplains chunking under RAG, follow-up drills specifically into chunking).
- **Curriculum-aware personalization**: an internal "concept graph" tracks topic mastery in real time (e.g., RAG → Vector DBs → Agentic AI → Deployment) and adjusts difficulty/topic order live. This is shown visibly to the user as a **topic progress map**.
- **"Why this question next"** indicator — small UI element showing the adaptive engine's reasoning in plain language (e.g., "Following up on vector indexing since your last answer was incomplete").
- **Coding interview mode**: in-browser code editor (syntax highlighting, multiple languages), candidate writes/runs code, AI evaluates logic/correctness/complexity, can ask to explain approach verbally.
- **Anti-cheat / Copy Detection**: if candidate switches browser tab, minimizes window, or the screen-share stops, the interview is flagged and auto-ends (with a warning grace-window — see Design Doc §7).
- **Memory across session**: AI references earlier answers later in the same interview (e.g., "Earlier you mentioned using FAISS — does that choice hold for this new scenario?").
- **Anti-hallucination**: technical questions and fact-checks are grounded against a verified question bank / knowledge base (RAG), not freeform LLM generation, especially for objectively-correct topics (algorithms, complexity, indexing methods).

### 4.5 Evaluation & Scorecard
- Rubric-based scoring **per topic**, not a single vague number. Each topic has explicit evaluation criteria.
- Specific, citation-style feedback ("You did not clearly distinguish cosine similarity vs dot product") rather than generic praise/criticism.
- Single fused report combining **technical depth** and **communication quality** (pace, filler words, clarity) in one view.
- Weak Areas + Strong Areas breakdown.
- **"Generate Roadmap"** button on weak areas → produces a structured learning roadmap (topics, resources, suggested order) for that candidate's specific gaps.

### 4.6 Interview History
- All past sessions stored per user: date, type, company-style, overall score, topic breakdown.
- Candidate can open any past session to see full transcript + scorecard.
- Trend view: score over time per topic (this sells well to judges/investors — "shareable report link" is a stretch goal).

### 4.7 Multi-language Support
- Candidate can select interview language from a supported list.
- Questions/UI are translated; candidate can answer in selected language; system still evaluates technical correctness in a language-agnostic way (translate answer → canonical evaluation).

### 4.8 Browser Compatibility Handling
- Web Speech API is Chrome-first. App must detect unsupported browsers and either (a) show a clear compatibility warning, or (b) fall back to a paid STT/TTS provider (see Tech Stack doc) so the experience doesn't silently break.

## 5. Non-Functional Requirements

- **Latency**: voice responses must stream, not wait for full LLM completion — target first-audio-byte under ~1.5–2s.
- **Reliability**: interview session state must survive brief network drops without losing progress.
- **Security**: resumes and transcripts are private per user; auth tokens must be verified server-side on every API call, not trusted from the client.
- **Scalability (post-MVP)**: architecture should not block adding more question topics/companies without code rewrites (question bank must be data-driven, not hardcoded in prompts).
- **Deployability**: must be a single-command-deployable frontend + backend (Vercel + Render/Railway), env-var driven, no hardcoded secrets.

---

## 6. Explicitly Out of Scope for MVP
- Payments / billing (B2B page is a marketing page only in MVP, no live pricing engine).
- Mobile native apps (web-responsive only).
- Multi-interviewer panel simulation.
- Video-based facial expression analysis (screen/camera are for proctoring only in MVP, not emotion AI).

---

## 7. Success Metrics (for demo/judging)
- End-to-end flow works: signup → resume upload → ATS score → interview (both types) → scorecard → roadmap → history, with zero manual intervention.
- Scorecard feedback is specific and cites transcript moments, not generic.
- Tab-switch triggers visible interview termination within the demo.
- At least 3 languages supported end-to-end (question + voice) for the demo.

## 8. Build Phases (high-level — full detail in Tech Stack doc)

1. **Phase 0** — Repo setup, env contract, auth (Google/GitHub/Phone) working end-to-end.
2. **Phase 1** — Resume upload + parsing + ATS scoring.
3. **Phase 2** — Question bank + adaptive engine (text-only interview, no voice yet).
4. **Phase 3** — Voice pipeline (STT/TTS, streaming) + mic/camera/screen-share + anti-cheat.
5. **Phase 4** — Coding interview mode (code editor + execution + evaluation).
6. **Phase 5** — Evaluation engine + scorecard + roadmap generation.
7. **Phase 6** — History, dashboard, multi-language layer.
8. **Phase 7** — Polish, landing page, B2B page, deployment.

Each phase must be independently testable before the next begins (see Tech Stack doc §"Phase-by-Phase Plan" for exact test checkpoints).
